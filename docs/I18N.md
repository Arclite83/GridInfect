# Internationalization — goal state

The game ships in more than one language without a fork, without a second
build, and without a layout that only works in English. This file is the
specification for that state: what the text stack is, where strings live,
how the player picks a language, and the layout rules every screen written
from here on obeys whether or not the language it was written for is
right-to-left.

Amend this file in the same change that amends the code (`ARCHITECTURE.md`
§9). The derivation gates in §4 are what keep it honest mechanically.

## 0. Why the current state blocks it

Four findings from the audit, each of which the sections below answer.

| Finding | Where |
|---|---|
| Text is Unity's legacy `TextMesh` on dynamic OS fonts. No shaping, no bidi, no wrap, no auto-fit. `renderer.sharedMaterial` is cached with no `Font.textureRebuilt` subscription, so a growing atlas garbles live text — latent today because the charset is Latin caps and digits | `Game/Ui/Ui.cs:36-78`, `:112-133` |
| Chip widths are computed from `label.Length`; one badge box is hardcoded to eight characters; body type size is capped by "the rules sheet's longest line" in English | `Game/Screens/BoardScreen.cs:55`, `:83`, `Game/PresentationConfig.cs:118`, `Game/Screens/DailyScreen.cs:271` |
| Two user-facing strings live in `GridInfect.Core`, which is the pure rules assembly: the ten tutorial sentences and the sixteen world names | `Core/Levels/TutorialLevels.cs`, `Core/Levels/WorldData.g.cs:33-51` |
| `ToUpperInvariant()` is applied to display text in five screens. Wrong for Turkish, meaningless for scripts without case | `Game/Screens/WorldSelectScreen.cs:80,143`, `FreePlayMenuScreen.cs:32`, `BoardScreen.cs:266,281,737`, `SettingsScreen.cs:76` |

Roughly 150 user-facing strings across twelve files, all literals or
interpolations in procedural C#. There is no string table, no key space and
no culture plumbing.

## 1. Text stack

**TextMeshPro replaces `TextMesh`.** It is the only stack that does not bake
a permanent language ceiling into the game: real text measurement
(`GetPreferredValues`), word wrap, `enableAutoSizing`, and font fallback
chains. The migration is contained because every text object in the game is
built by one factory (`Ui.MakeText`, `Game/Ui/Ui.cs:112`) and every button
label by one more (`UiButton.Make`, `:212`). The work is a field-type swap
across eleven files behind an unchanged signature, not a rewrite.

**Fonts ship as assets.** Chakra Petch and Share Tech Mono are both OFL.
Vendoring them removes the current situation where `FindFont` probes the OS
and cannot guarantee the design face (`Ui.cs:36-52`). CJK arrives as a
fallback font asset subset at build time to the glyphs the shipped
translations actually use; the unsubset Noto CJK faces are too large to ship
whole for a game with 150 strings.

Not in scope, and why:

- **UI Toolkit's Advanced Text Generator** (HarfBuzz/ICU/FreeType) is the
  only Unity-native path to Arabic shaping and bidi. It is UI Toolkit-scoped
  and does not apply to TextMeshPro objects. This project has zero UI
  Toolkit and all its text is worldspace, so reaching ATG means rewriting
  the UI onto UI Toolkit. Deferred with Arabic (§10).
- **`com.unity.localization`** is a data and asset management layer: locales,
  string tables, Smart Strings, Addressables loading. It has no bidi and no
  shaping, and its table model duplicates the bake pipeline this repo already
  has (§4). Not taken.

## 2. Language set

Identity is a **BCP-47 tag**, everywhere, always. Never a list index (breaks
on insert), never a mark id (couples data to art).

| Tag | Script tier | Selector mark | Release |
|---|---|---|---|
| `en` | Latin | chip only | v1 |
| `de`, `fr`, `es`, `pt-BR`, `it`, `tr` | Latin | chip only | v1 |
| `ru` | Cyrillic | `Я` | v1 |
| `ja` | CJK | `日` | v1 |
| `ko` | CJK | `한` | later |
| `zh-Hans` | CJK | `简` | later |
| `zh-Hant` | CJK | `繁` | later |

One tag per language. **No regional variants of the same language ship
together.** That constraint is what makes a compact selector unambiguous: a
player never hunts for a second Spanish, so `es` needs no country
qualification. `pt-BR` is tagged for its region because Brazilian and
European Portuguese differ enough to matter and only one of them ships.

**v1 is the Latin tier plus Cyrillic plus Japanese.** Japanese is in the
first release deliberately and is not a translation-budget decision: it is
the one language in v1 that exercises the CJK font subset, the fallback
chain and a drawn script mark. Shipping the pipeline with only Latin
languages would leave all three unvalidated and satisfy §12.8 on a
technicality. Korean and both Chinese scripts follow once that path is
proven, at translation cost only.

Which Latin-tier languages earn their translation spend is a store-data
question (installs by country), not an engineering one. The pipeline is
indifferent to the count, so that list can be trimmed at stage 6 without
touching stages 1 to 5.

## 3. Selector

**Mono glass chip carrying the ISO code, plus a drawn script mark for
languages whose readers cannot read Latin script.**

- Every entry is a glass chip with its tag in the mono face, in the
  silkscreen idiom the HUD already speaks (`GI-CAL REV B`, `SOLVE 03`, `T3`).
- Non-Latin entries additionally carry a drawn mark from their own script,
  per the table in §2.
- Latin entries carry no mark. A German reader can read `DE`; inventing a
  decorative letterform per Latin language buys nothing and creates
  ambiguity, since `ç` is French, Portuguese and Turkish at once.

The mark exists to serve a reader who cannot read the chip. That is the
whole rule, and it is why the mark set is exactly the non-Latin scripts.

**No flags.** Flags name countries, not languages, and the cases where that
breaks are the cases that matter most: Arabic has twenty-two countries and no
correct flag, and Chinese script choice expressed as a flag becomes a
territorial claim rather than an encoding. Script marks are accurate, politically
inert, and cheaper — the expensive flags to draw at chip size are exactly the
ones with emblems (Korea, Brazil, Portugal, India), and this avoids all of them.

**Marks are outlines, not typeset text.** They come through the existing
pipeline: `grid-infect-style/gen-logo.mjs` already extracts glyph outlines
via opentype.js and emits `Game/View/LogoGlyphs.g.cs` (nine Latin letters in
1/1000 em), rasterized at runtime by `View/GlyphRaster.cs`. A sibling
generator emits `Game/View/SelectorGlyphs.g.cs` the same way. No font in the
build for the selector, no atlas, and no dependency on having already loaded
the script being offered.

**Placement:** a sub-screen reached from SETTINGS, not a settings row. Twelve
or more entries do not fit `SettingsScreen`'s row stack, whose row count is
hardcoded per call (`Game/Screens/SettingsScreen.cs:32-37`). `RulesScreen`'s
pager is the closest existing pattern.

## 4. String pipeline

Source of truth is `docs/strings/<tag>.json`. `tools/bake_strings.py` emits
`Game/Strings.g.cs` — the adapter, not Core, because a string table is
presentation and Core holds no prose (§5). CI re-derives it and fails a stale bake, exactly
as `bake_worlds.py` and `bake_levels.py` already do (`ARCHITECTURE.md` §6).

Every language is baked into the binary. For 150 short strings across a dozen
languages that is tens of kilobytes, which buys zero boot IO, zero MiniJson
at startup, and a table the headless mirror suite can assert against. Runtime
JSON loading and `.resx` satellite assemblies both lose on those three counts.

**Gates**, both build-time derivations rather than source-scanning tests
(§6 of `ARCHITECTURE.md` forbids the latter):

- The baker fails when any `<tag>.json` key set differs from `en.json`.
  Missing and extra keys are both errors.
- It fails when a value's `{N}` placeholder set differs from `en.json`'s, so
  a translation cannot drop or invent a substitution.
- It fails when `world.<id>.name` does not match the name authored in
  `docs/worlds/<id>.jsonl` (case aside, since the rows are uppercase chips).
- It fails when a `tut.<n>.line` is empty, holds a hard break, or draws wider
  than the one-line band, measured East-Asian-width so CJK counts double.
  This ran as a Core test over English; in the baker it covers every
  language, which is where a too-long line actually comes from.
- CI re-runs the baker and fails when `Strings.g.cs` differs from the
  committed file.

## 5. Keys

**Keys derive from ids that already exist.** No new data fields, no
migration of `docs/worlds/*.jsonl`.

| Content | Key | Note |
|---|---|---|
| Tutorial step *n* | `tut.<n>.line`, 1-based | `TutorialLevels.Step.Line` is gone; the sentence stays beside its board as a comment. `TutorialTests` keeps the step count, which is what the lookup depends on |
| World `w01` | `world.<id>.name` | the JSONL `name` stays the naming authority and the baker cross-checks it. Ids are `w01`-`w12` and `w14`-`w17`; there is no `w13` |
| Everything else | `screen.element` | e.g. `menu.worlds`, `settings.reset`, `board.complete` |

`GridInfect.Core` holds keys and never prose. Lookup happens in the adapter.
This restores the assembly boundary the two current violations break.

## 6. Formatting

**Casing lives in the string table.** Delete every `ToUpperInvariant()` on
display text and author `en.json` with the caps already in it. Translators
then decide casing per language, which is the only correct answer for Turkish
and for scripts without case.

**Numbers format invariant.** Every in-game numeric is a scoreboard readout
in a mono column, not prose. `Queries.FormatDuration`
(`Core/Rules/Queries.cs:116-136`) appends longs with ambient culture and
would emit Arabic-Indic digits under an `ar` locale, breaking the column.
Pin `CultureInfo.InvariantCulture` there and at the display `.ToString()`
sites in `BoardScreen`, `DailyScreen`, `ClassicSelectScreen` and
`WorldSelectScreen`. `DailySpec`'s date key is already invariant and stays so
— it is a cache and save key, not display.

**No pluralization machinery.** Restructure the two count strings
(`DailyScreen.cs:342`, `"{n} BUGS · {n} CELLS"`) into the label-value form
the HUD already uses everywhere else: `BUGS 3 · CELLS 12`. Russian has three
plural forms and Arabic six; ICU MessageFormat is a real dependency and a
translator-training cost, and it buys nothing here.

**Month and weekday names are keys, not substrings.** `DailyScreen.cs:221`
and `:338` take `Substring(0, 3)` of a month name, which is wrong in Russian
and meaningless in Chinese. Short forms get their own keys
(`cal.month.01.short`).

## 7. Direction readiness

These rules apply to every screen written from now on, whether or not a
right-to-left language has shipped. They cost nothing while the game is
left-to-right and are expensive to retrofit.

**The mirror boundary is chrome versus board.** The board is the game's own
coordinate space (`loc = i*6 + j`), and arms, relay directions, tile
ordinals, the piece tray and every bug glyph derived from them **never**
mirror. Mirroring the board would change the puzzle. Chrome mirrors.

**Chrome has exactly one directional mark.** `BugGlyph.Chevron` at
`View/BugGlyph.cs:154`, used at ten call sites across five screens, uniformly
`prev → true` / `next → false` (`WorldSelectScreen.cs:40,42`,
`DailyScreen.cs:78,80`, `RulesScreen.cs:57,59`, `BoardScreen.cs:142,144`,
`ClassicSelectScreen.cs:42,44`). Those mirror, because reading order defines
which way forward is. Replace the literal bools with `Prev`/`Next` wrappers
that resolve from the layout direction. Every other mark in `BugGlyph`
depicts an object (gear, lock, check, question, trap, relay, repel, avoid,
dot) and does not mirror. No per-mark metadata is needed; the split falls on
the chrome/board boundary that already exists structurally.

**Layout carries a direction sign.** `PresentationConfig.Layout` gains one,
and anchored x-positions resolve through it. `TextAnchor.MiddleLeft` and
`MiddleRight`, currently chosen structurally, become leading and trailing and
resolve at build time.

**Strings are never a layout mechanism.** `BoardScreen.cs:721` uses literal
triple-spaces as columns (`"SOLVED {n}   STREAK {n}   BEST {n}"`), and
`DailyScreen.cs:342` uses `·` the same way. These become positioned elements.
They are already fragile under translation, before direction enters it.

**Size is measured, never counted.** Replace `label.Length * k` at
`BoardScreen.cs:55`, `:83` and `DailyScreen.cs:271` with
`TMP_Text.GetPreferredValues`. Replace the English-calibrated `BodyText` cap
at `PresentationConfig.cs:118` with auto-sizing floored at the documented
11 px legibility limit (`PresentationConfig.cs:230`).

**The calendar flips.** `DailyScreen` hardcodes Monday-first at `:106,159`
and pages months by swipe direction. Column order becomes a derived array;
the swipe routes through the direction sign.

## 8. Locale model

| Piece | Shape |
|---|---|
| Action | `settings.language`, input a BCP-47 tag string. Mirrors `settings.skin`: Core keeps the tag opaque, the adapter owns what it means (`Core/Actions/ProfileActions.cs:105-127` is the template) |
| Profile | `Lang` string beside `Muted` and `Skin` (`Core/Rules/GameState.cs:53-92`) |
| Save | `SaveCodec` v8 adds `"lang"`, following the `"skin"` shape (write `Profile/SaveCodec.cs:74`, read `:146-150`). Empty string means follow the device |
| Boot | `Application.systemLanguage` maps to the shipped set, falling back to `en`. A stored non-empty tag overrides it |
| Switch | Instant rebuild of the current screen, as `SettingsScreen.Choose()` already does for skin (`:155-164`). Screens are constructed fresh on `Show`, so nothing else needs invalidating |

## 9. Pseudolocales

Two generated languages, emitted by the baker from `en.json`, shipped as
hidden dev entries. They are what makes §7 enforced rather than aspirational.

- `qps-ploc` — brackets each string and pads it 40% longer with accented
  Latin. Catches every overflow, clipped box and length-derived width in one
  pass, in English, with no translator.
- `qps-plocm` — reverses and adds RTL marks. Catches directional layout bugs
  before any RTL language exists.

## 10. Deferred: Arabic and Hebrew

On the roadmap, not in this scope. Both are gated on shaping, which §1
establishes TextMeshPro does not do.

Hebrew needs bidi but no contextual joining, so it is materially cheaper than
Arabic, which needs joining and lam-alef ligatures. On TMP the path for both
is a preprocessing plugin (RTLTMPro, MIT, covers Arabic, Farsi and Hebrew)
that rewrites strings into Unicode Presentation Forms before TMP sees them,
plus font assets carrying U+0600–06FF and both Presentation Forms blocks.
The alternative is the UI Toolkit rewrite that unlocks ATG.

§7 is the reason this stays a bounded addition rather than a rewrite: when
Arabic lands, the remaining work is the shaping layer, the font, and a QA
pass. No layout is re-cut.

## 11. Explicit non-goals

- **No alternate build, for any market.** Mainland China distribution is not
  reachable by a self-publisher on Google Play and the global App Store
  anyway: Google Play does not operate there, local Android stores require a
  publishing partner, and monetized games need a 版号 license on both
  platforms. Script marks make the question moot in the product. If a China
  publishing deal ever happens, the partner specifies what changes then.
- **The wordmark stays Latin.** `LogoGlyphs.g.cs` holds nine baked outlines
  for `G R I D N F E C T`. It is a logo.
- **No machine translation of the tutorial without native review.** The ten
  sentences in §5 are the entire instruction set for a game that teaches
  nothing else. A mistranslation of "A ray may never touch an avoid cell"
  produces a player who believes the game is broken.

## 12. Acceptance criteria

1. `dotnet test src/Tests.Mirror` and the Unity edit-mode suite pass
   unchanged. No rules, solver, generator or save golden moves.
2. `tools/bake_strings.py` output matches the committed `Strings.g.cs`; CI
   fails a stale bake and fails a key-set mismatch between any `<tag>.json`
   and `en.json`.
3. `grep -r ToUpperInvariant unity/Assets/_Project/Game/Screens` returns
   nothing on display text.
4. No user-facing prose remains in `GridInfect.Core`.
5. `qps-ploc` renders every screen with no clipped, overlapping or
   ellipsized text at 390×844 and at the narrowest supported width.
6. `qps-plocm` renders every screen with chrome mirrored, the board
   unmirrored, and pager chevrons pointing the correct way.
7. Language switch from the selector redraws the current screen and survives
   a save/load round trip.
8. At least one non-Latin language ships in the same release as the
   pipeline. Shipping the machinery with only English in it does not
   demonstrate that §7 was done.

## 13. Stages

**This block runs after stage 6 of `EXECUTION_PLAN.md` unblocks.** The ads
and consent wiring is waiting on SDK packages and an Android device build,
and the TextMeshPro migration touches every screen in the game. Running them
concurrently guarantees conflict in the adapter. Ads first, i18n second, no
overlap.

That ordering has one cost worth naming: every screen written between now
and then is written before §7 exists in code. §7 is therefore binding on new
work immediately, ahead of its own stage. Writing a new screen with hardcoded
left/right anchors and length-derived widths is cheap now and expensive in
stage 4.

Run the stages themselves serially.

| # | Stage | Delegable |
|---|---|---|
| 1 | TMP swap behind the existing `Ui.MakeText` / `UiButton.Make` signatures. English only, no behavior change. Vendor the two OFL fonts | No — needs the editor (see §14) |
| 2 | Layout re-fit: measured widths, auto-size with the 11 px floor, the eight-character badge, month short-form keys | No. Needs the style guide and a human eye |
| 3 | Extraction: `en.json`, the baker, the CI gate, keys into Core, casing into the table, invariant numerics, plurals restructured | Yes |
| 4 | Direction readiness per §7: direction sign, leading/trailing anchors, `Prev`/`Next` chevrons, calendar column order, positioned HUD elements | Yes, mechanical against §7 |
| 5 | Selector: `SelectorGlyphs.g.cs` generator, the sub-screen, `settings.language`, `SaveCodec` v8, boot detection | Mixed. The generator yes, the screen no |
| 6 | Pseudolocales, then the v1 language set. Japanese first of the real ones, since it is the one that proves the CJK path | Translation is external. Never machine-translate the tutorial (§11) |

Stage 5 is where the `ARCHITECTURE.md` §3 action registry gains its
`settings.language` row, and §2 the `Profile` field.

## 14. As built (2026-09-10)

Stages 3, 4 and 5 are in, in that order, on top of the ads cadence merge.
Stages 1 and 2 are not, deliberately: the `TextMesh` → TextMeshPro swap
changes how every piece of text is sized (`characterSize` against a 64 pt
face is not TMP's `fontSize`), and the headless mirror compiles the adapter
against hand-written API stubs, so a blind swap would be self-certifying.
It lands as its own commit once someone can look at it. Nothing done so far
depends on it: the extraction, the direction sign and the selector all run
on the renderer the game already has, and render exactly as before in
English.

Deviations from the sections above, all pending stage 2 (they need
measurement, which needs TMP):

- The three-readout HUD captions (`SOLVED n   STREAK n   BEST n`, and the
  Free Play clock line) are still one string joined by spacing. The keys are
  already split (`board.hud.*`), so the fix is positioning, not translation.
- `Badge` in `DailyScreen` and `ChipSize` in `BoardScreen` still size from
  `text.Length`. Under `qps-ploc` the padding makes them wide enough by
  accident; under a real CJK translation they will be narrow.
- `BodyText` is still capped by the English rules sheet.

**Test checklist for the editor** (everything here is Play-mode, no device
needed):

1. Open with a fresh save: every screen reads exactly as before. The only
   visible change is a LANGUAGE row in SETTINGS.
2. SETTINGS → LANGUAGE: AUTO lit, `EN`, `QPS-PLOC`, `QPS-PLOCM` present
   (the two pseudolocales only because this is the editor). Tap `EN`: the
   screen rebuilds with EN lit, nothing else changes. Stop and Play again:
   still EN. Tap AUTO: back to following the device.
3. Tap `QPS-PLOC`, then walk every screen: menu, tutorial offer, worlds and
   a world, a board in each mode, the daily calendar, endless, legacy,
   rules (all pages), settings. Everything reads `[Ĺíkéé thíš··]`. What to
   look for is any label clipped by its chip, any line off the edge of the
   screen, and any two texts overlapping. Those are stage 2's list; note
   them, they are expected. What should not happen is a blank label, a
   missing chip, or an exception in the console.
4. Tap `QPS-PLOCM`. The back chip is now top-right; pager chevrons have
   swapped ends and directions; the calendar runs Monday from the right and
   a swipe to the left goes to the previous month; the rules legend's
   swatches hang off the right with text to their left; the solved popup's
   MENU is on the right. The board, its tray, every bug's arms and the
   relay marks are untouched. Text renders reversed with a mark at each end
   — that is `TextMesh` having no bidi and is the whole reason stage 1
   exists; the layout is what this pass proves.
5. Erase progress with a non-AUTO language set: the language survives.
6. Quit with `QPS-PLOCM` set, edit the save file's `"lang"` to `"xx"`, open:
   the game is in English (an unshipped tag falls back to the device), and
   LANGUAGE shows AUTO lit because the malformed tag was dropped on load.
   Set it to `"de"`: same, since `de` does not ship yet — but the tag is
   kept, so the day `de` ships the choice comes back.
